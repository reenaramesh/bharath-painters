    What this preview commits to

    1. Any entry is movable, shared ones included. Curated order is stored per user in a new MasterDataSortPreference(user, section, entry_id, position) table, so reordering writes to your preferences and never to the shared master row.

    2. The existing sort_order column keeps its job as the default order for anyone who has not ranked a section, and as the fallback tail under your ranked rows. Nothing is backfilled into the new table — an untouched section behaves exactly as today.

    3. Arrows and drag both call a single commitOrder, which POSTs the full unfiltered id list. This matters: the list can be filtered by search text or a service-type chip, and sending only the visible subset would silently wipe the ranks of every hidden row. Backend upserts by id and never deletes omitted rows, so even a bad payload degrades instead of corrupting.

    4. Arrow disabled states read the index in the full list, not the filtered view — the current build disables the wrong rows whenever a filter is on.

    5. Ordering is applied in SQL via Case/When inside visible_master_data(), so all ~11 dropdown consumers (quotations, invoices, measurements, work changes) pick it up with no change to them. It stays a queryset, which WorkDescriptionListCreateView requires because it chains .select_related("service_type").

    6. Reset to default order posts an empty list and deletes your preferences for that section, returning you to the admin-set order.

    Preview only — no application file was changed. Drag needs a mouse; the arrows cover touch and Firefox.
